# P7-003C — Versioned Retrieval Recall@5 Baseline

**Status:** DONE

## Task ID

P7-003C

## Goal

Create a small versioned logical retrieval dataset and measure the current
scoped exact-vector Knowledge path with per-case and macro Recall@5.

## Why Now

P6/P7 prove that retrieval works and is isolated, but they make no retrieval-
quality claim. A fixed baseline is required before a future task can justify
BM25, hybrid retrieval, RRF, reranking, query rewrite, or ANN tuning.

## Scope

- Add a versioned JSON manifest with top-level logical Projects/Documents and
  retrieval cases. Use `project_key`, `document_key`, and zero-based
  `chunk_index`; commit no generated UUIDs.
- Start with a manually reviewable set of at least three cases across at least
  two Documents, including distractor passages and at least one case with more
  than one relevant passage.
- Validate unique logical keys, referential integrity, non-empty relevant sets,
  and that each case has at most five relevant passages.
- In an isolated `researchflow_test` setup, create runtime users/Projects,
  ingest Markdown through the existing Backend API, and resolve generated IDs
  only for evaluation.
- Query the existing scoped Knowledge search API with `limit=5` using the real
  configured `BAAI/bge-m3` path and pgvector.
- Compute per-case Recall@5 and unweighted macro Recall@5. Add deterministic
  unit tests for the formula and logical-to-runtime resolver.
- Record a credential-safe baseline with dataset version, model, K, per-case
  result, macro result, and run time. Do not set a pass/fail product threshold.

## Out of Scope

- Production API/schema changes, a Chunk read endpoint, persisted evaluation
  runs, dashboards, LangSmith, or CI secrets.
- MRR, NDCG, Precision@K, answer relevance, faithfulness, citation correctness,
  Agent Tool choice, latency/cost budgets, or product quality thresholds.
- Changing fixture labels after seeing results merely to improve the metric.
- BM25, hybrid retrieval, RRF, reranking, query rewriting, ANN indexes/tuning,
  chunking changes, or embedding-model changes.

## Acceptance Criteria

- The fixture contains no runtime `user_id`, `project_id`, `document_id`, or
  `chunk_id`, and its relevance labels survive re-ingestion with new UUIDs.
- Evaluation setup refuses the production database, uses isolated Project
  scope, and leaves production APIs/models unchanged.
- Ground-truth resolution uses the current deterministic chunk index; generated
  IDs stay in memory/test setup and are not written back to the fixture.
- Search is exercised through the existing scoped Backend endpoint with
  `limit=5`; the evaluator does not call retrieval internals to fabricate the
  measured ranking.
- Formula tests prove exact-match, partial-recall, zero-hit, and macro-average
  cases. Every dataset case has at least one relevant passage.
- One real configured embedding/pgvector run records numeric per-case and macro
  Recall@5 without secrets, vectors, or random runtime IDs.
- A poor baseline remains a valid result. No algorithm, label, or threshold is
  changed inside this task to turn it green.
- Existing regression, dependency, migration-drift, and `git diff --check`
  gates pass without unrelated changes.
