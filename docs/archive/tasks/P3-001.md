## Required Operations

### 1. Add the local PostgreSQL environment

Create a root `compose.yaml` with exactly one `postgres` service:

- image: official `postgres:18.6`;
- host binding: `127.0.0.1:5432:5432`;
- local-only values:
  - user: `researchflow`;
  - password: `researchflow_dev_only`;
  - development database: `researchflow`;
- one named volume mounted at `/var/lib/postgresql`;
- a `pg_isready` health check;
- an initialization directory mounted read-only at
  `/docker-entrypoint-initdb.d`.

Add one initialization script at
`docker/postgres/init/001-create-test-database.sql` which creates
`researchflow_test` owned by `researchflow`.

These fixed credentials are deliberately non-secret local development values.
Do not add `container_name`, Adminer/pgAdmin, Redis, an application container,
or a custom network. Do not make the initialization SQL pretend to support
arbitrary user/database overrides.

The PostgreSQL 18 image uses `/var/lib/postgresql` as the volume target. Record
that entrypoint initialization scripts run only when the data volume is empty.
Do not use `docker compose down -v` as a routine command; deleting the volume is
a destructive reset requiring explicit user intent.

### 2. Add explicit Backend configuration

Append these examples to `.env.example`:

```dotenv
RESEARCHFLOW_DATABASE_URL=postgresql+psycopg://researchflow:researchflow_dev_only@127.0.0.1:5432/researchflow
RESEARCHFLOW_TEST_DATABASE_URL=postgresql+psycopg://researchflow:researchflow_dev_only@127.0.0.1:5432/researchflow_test
```

The Backend reads `RESEARCHFLOW_DATABASE_URL` from the environment. Missing
configuration is a startup/configuration error. A configured database that
cannot answer the readiness query produces the approved sanitized `503`
response.

Tests must read `RESEARCHFLOW_TEST_DATABASE_URL` explicitly. They must refuse
destructive cleanup when the test URL is missing, equals the runtime URL, or
does not name the approved `researchflow_test` database.

Do not add a settings framework or silently fall back to SQLite.

### 3. Add only the required dependencies

In `pyproject.toml`, add a `backend` optional dependency group containing:

- FastAPI;
- Uvicorn;
- SQLAlchemy 2.x;
- Alembic;
- Psycopg 3 with the binary extra for local development.

Add `httpx` to the existing `dev` group if it is required by FastAPI's test
client. Avoid unrelated packages.

### 4. Add the initial Alembic migration

Keep Alembic configuration in `pyproject.toml` and revision files under
`migrations/`. The first migration creates only the approved `projects` table:

| Column | PostgreSQL Contract |
| --- | --- |
| `project_id` | `uuid`, primary key, application supplies UUID v4 |
| `name` | `varchar(120)`, not null, database non-empty check, not unique |
| `created_at` | `timestamptz`, not null, server default `CURRENT_TIMESTAMP` |

The migration must upgrade an empty development database and an empty test
database. Do not add `updated_at`, user/tenant columns, LangGraph IDs, or
speculative foreign keys.

### 5. Implement the minimal Backend package

Use ASGI entrypoint `researchflow.backend.app:app`. A sufficient starting
shape is:

```text
src/researchflow/backend/
  __init__.py
  app.py
  database.py
  projects.py
```

- `database.py`: synchronous engine, session factory, and request-scoped
  session dependency.
- `projects.py`: the concrete Project mapping, request/response Schemas,
  create/read operations, and router. Keeping these together is intentional
  for the first resource.
- `app.py`: FastAPI application, router registration, and database readiness
  endpoint.

Use synchronous SQLAlchemy 2.x and synchronous FastAPI path operations.
Generate `project_id` with Python UUID v4 before insertion. Let PostgreSQL
generate `created_at`, then return it as a timezone-aware UTC value. Keep
transactions request-scoped and roll back failed writes.

Do not add repository interfaces, generic CRUD/service base classes, an async
database stack, dependency-injection frameworks, or Agent logic.

### 6. Implement the approved HTTP Contract

Implement exactly:

- `GET /health`;
- `POST /projects`;
- `GET /projects/{project_id}`.

Follow `docs/API_CONTRACTS.md`, including trimming, 1–120 character validation,
forbidden extra request fields, duplicate-name behavior, canonical UUIDs,
standard `422` responses, sanitized database `503`, and Project `404`.

Do not add list, update, or delete endpoints.

### 7. Add focused PostgreSQL-backed tests

At minimum verify:

- healthy database readiness and sanitized unavailable-database behavior;
- create returns `201`, a UUID, the trimmed name, and an aware timestamp;
- the created Project can be read by ID;
- duplicate names create different Projects;
- blank/too-long/non-string names and extra fields return `422`;
- an invalid UUID returns `422`;
- an unknown valid UUID returns the approved `404` response;
- pre-existing Agent tests still pass.

Use the real test PostgreSQL database, not SQLite. Guard any table truncation or
other cleanup so it can target only `researchflow_test`.

### 8. Document the local runbook

Create `docs/BACKEND_LOCAL_DEV.md` with PowerShell commands for:

1. confirming that Docker Desktop's Server is reachable with `docker version`;
2. validating config with `docker compose config`;
3. starting only PostgreSQL with `docker compose up -d postgres`;
4. confirming health with `docker compose ps` and `pg_isready`;
5. installing `.[backend,dev]`;
6. setting the two database URL environment variables without overwriting an
   existing `.env` file;
7. applying Alembic to development and test databases;
8. running Backend plus existing Agent tests;
9. starting Uvicorn and smoke-testing health, create, and read;
10. stopping the service without deleting its volume.

Document that volume deletion loses local databases and that initialization
scripts do not rerun against an existing volume.
