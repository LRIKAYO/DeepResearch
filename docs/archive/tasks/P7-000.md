# P7-000 — Agent Knowledge Boundary Architecture Decision Brief

**Status:** DONE — 00-Architect accepted D-015 on 2026-09-05; P7-001 and
P7-002 are DONE.

This document records the next Contract task after Phase 6, the options reviewed
by 00-Architect, and the accepted boundary. It authorizes P7-001 only; no
implementation begins in P7-000.

## Architect Decision

00-Architect selected:

- **ADR-P7-A: A1, local/test only.** LangGraph Run context carries immutable
  `knowledge_scope = {user_id: UUID, project_id: UUID}` outside Agent State and
  model Tool arguments. The carrier is not authority. This makes no production
  security claim; production remains blocked on a trusted injector, signed
  capability, or gateway/proxy decision.
- **ADR-P7-B: B1.** A typed Agent HTTP client calls Product Backend with a
  10-second total timeout and no retry. Only `200 []` maps to empty Evidence.
  Authentication, authorization, validation, timeout, network, and Backend
  failure become sanitized explicit Tool failures.
- **ADR-P7-C: C1.** Agent uses one discriminated Pydantic Evidence union. P7
  accepts only `temporary_research` and `user_upload`; a user-upload item keeps
  `document_id`, `chunk_id`, and `filename`. Existing provisional checkpoints
  have a clean break rather than an implicit schema migration. Saved Web Source
  remains unimplemented until its Product lifecycle is approved.
- **ADR-P7-D: D1.** Agent owns an explicit two-Tool registry. It validates all
  requested Tool names before execution, then executes calls sequentially in
  model call order. Repeated calls are allowed. Any failure fails the whole
  node; there is no retry or partial-success Evidence.

P7-001 may implement the scoped HTTP client, approved Evidence models, and
unbound `knowledge_search()` Tool. P7-002 remains a separate activation point
for changing the Research Graph from one Tool to two.

## Current Verified Baseline

- Product Backend owns Project membership and exposes
  `POST /projects/{project_id}/knowledge/search`.
- The authoritative retrieval query joins Chunk to Document to Project and
  filters `documents.project_id` plus `projects.owner_user_id` before ordering
  and limit.
- Product Backend reads the opaque user UUID from the trusted
  `X-ResearchFlow-User-Id` boundary. The current browser-supplied local value is
  explicitly not production authentication.
- `KnowledgeHit` contains `document_id`, `chunk_id`, `filename`, `content`, and
  `score`.
- Agent `Evidence` currently contains only `source`, `content`, and optional
  `relevance_note`.
- Agent State deliberately contains no `user_id`, `project_id`, session ID, or
  thread authority.
- LangGraph thread metadata is diagnostic projection, not Project-membership
  authority.
- The current graph binds exactly one concrete `web_search` Tool. Its executor
  rejects every other tool name and accepts only the current three Evidence
  fields.

## Non-negotiable Constraints

- Agent must use a `knowledge_search()` boundary and must not import pgvector,
  SQLAlchemy retrieval code, or database models.
- Knowledge does not control the Research Graph or decide when Web versus
  permanent Knowledge is searched.
- Neither model-generated Tool arguments nor thread metadata may grant Project
  access.
- Backend must remain the final user-and-Project authorization boundary even if
  an upstream component already validated scope.
- `KnowledgeHit` must not be silently relabelled as the current Evidence shape
  while dropping Document/Chunk provenance.
- Do not create parallel Web Evidence and Knowledge Evidence systems. Any
  Evidence Schema change requires 00-Architect approval.
- Temporary Web Research remains session-scoped and is not permanently
  embedded. A Saved Web Source enters permanent Project Knowledge only after an
  explicit user save action and a future ingestion task.

## ADR-P7-A — Trusted Project Scope Handoff to Agent

### Problem

`knowledge_search()` needs `user_id + project_id`, but those values must not be
model-controlled, inferred from text, copied into Agent State as business
authority, or recovered from thread metadata. The current direct browser to
Agent Server path has no production authenticator.

### Option A1 — Trusted Runtime Context Contract, Local-only Carrier

Define an immutable per-run `KnowledgeScope` containing `user_id` and
`project_id`. A trusted runtime boundary supplies it separately from Agent
State and Tool arguments. P7 implementation and tests inject this context; the
local browser carrier remains explicitly non-production until a gateway or
authenticator exists.

- **Benefit:** smallest next slice; preserves the current direct Agent stream
  and keeps product IDs out of checkpointed state.
- **Cost:** does not make the current local browser topology production-safe.
- **02-Knowledge recommendation:** choose A1 for the next local vertical slice,
  with an explicit deployment stop gate.

### Option A2 — Backend-issued Signed Project Capability

After validating user/session/Project membership, Backend issues a short-lived,
signed scope capability. The browser carries it to Agent Server; Agent verifies
it and derives immutable runtime scope.

- **Benefit:** preserves direct streaming while preventing arbitrary scope
  substitution.
- **Cost:** introduces signing keys, expiry, replay, refresh, and failure
  Contracts; this is a new security subsystem.

### Option A3 — Trusted Gateway or Backend Agent Proxy

Place Agent execution behind a component that authenticates the user, resolves
Project membership, strips untrusted scope headers, and injects verified runtime
context.

- **Benefit:** central authority and a clearer production trust boundary.
- **Cost:** changes the P5 direct-stream topology and expands transport,
  streaming, deployment, and failure scope.

### Rejected Carriers

- Model-generated `user_id` or `project_id` Tool arguments.
- `AgentState` fields treated as membership authority.
- LangGraph thread metadata treated as membership authority.
- An arbitrary public `X-ResearchFlow-User-Id` supplied by the browser.

### Required Architect Decision

Select A1, A2, or A3 and state whether the decision authorizes only local
development or a production security claim. Also define the immutable runtime
input name and the component responsible for creating it.

## ADR-P7-B — Agent-to-Knowledge Invocation Boundary

### Option B1 — Product Backend HTTP API

The Agent Tool calls the existing scoped Backend endpoint through a small typed
client. It supplies trusted runtime scope, query, and limit; Backend performs
authorization, embeddings, and retrieval and returns `KnowledgeHit` values.

- **Benefit:** preserves service ownership and the already-tested authorization
  query; Agent knows no storage implementation.
- **Cost:** adds one internal HTTP dependency and its timeout/error Contract.
- **02-Knowledge recommendation:** choose B1.

### Option B2 — Direct Python Knowledge Retrieval

The Agent imports Knowledge retrieval functions and connects to PostgreSQL.

- **Benefit:** avoids an HTTP hop.
- **Cost:** bypasses the Product Backend authorization/API boundary and couples
  Agent runtime to database configuration and persistence models.
- **02-Knowledge recommendation:** reject B2.

### Required Architect Decision

Confirm the call direction and define timeout, unavailable-service behavior,
and whether Backend `401`, `404`, `422`, and `503` become Tool errors or empty
Evidence. Recommendation: authorization/validation/unavailability are explicit
Tool failures; only a successful empty hit list becomes empty Evidence.

## ADR-P7-C — Unified Evidence and Provenance Contract

### Problem

The current Evidence fields cannot preserve `document_id` and `chunk_id`, while
`KnowledgeHit` is not an Agent Evidence or final Citation. Mapping only
`filename → source` and `content → content` would lose durable citation
provenance.

### Option C1 — One Evidence Envelope with Discriminated Provenance

Keep one Agent Evidence collection and add a stable common envelope plus a
source-specific provenance variant.

Proposed conceptual shape:

```text
Evidence
  content: string
  source_type: temporary_research | user_upload | saved_web_source
  source_label: string
  relevance_note?: string
  retrieval_score?: number
  provenance:
    TemporaryWebProvenance { url, captured_at? }
    ProjectDocumentProvenance { document_id, chunk_id, filename,
                                page_number?, section_path? }
    SavedWebProvenance       { saved_source_id, url, captured_at? }
```

Only variants backed by an approved lifecycle are implemented. P7 may implement
`temporary_research` and the current Markdown `user_upload`; Saved Web remains
a reserved design direction until its Product model is approved.

- **Benefit:** one Evidence collection can retain citation-grade provenance
  without forcing every source to have meaningless fields.
- **Cost:** changes Agent validation, tests, Writer input, and checkpointed
  internal state.
- **02-Knowledge recommendation:** choose C1, but let 00-Architect approve exact
  names, required fields, and compatibility policy.

### Option C2 — Keep Current Evidence and Return Raw KnowledgeHit Separately

- **Benefit:** avoids changing existing Web Evidence immediately.
- **Cost:** creates parallel evidence paths and pushes fusion/citation ambiguity
  downstream.
- **02-Knowledge recommendation:** reject C2.

### Required Architect Decision

Approve the unified shape, exact source-type vocabulary, provenance variants,
and migration policy for existing Web Tool tests/checkpoints. Decide whether
runtime validation remains manual dictionaries or moves to one shared typed
validation model; do not introduce both.

## ADR-P7-D — Multiple Evidence Tools in the Agent Graph

### Problem

The current graph accepts exactly one concrete Tool. Adding
`knowledge_search()` while retaining `web_search` changes the executor and
routing Contract.

### Option D1 — Bounded Registry of Approved Evidence Tools

`build_graph` receives a small explicit set of evidence-producing Tools. The
Researcher sees both schemas. The executor validates every requested name
before any Tool runs, executes deterministically, validates all results against
the unified Evidence Contract, and flattens them into one Evidence collection.

- **Benefit:** preserves the existing validate-before-side-effects rule and
  keeps orchestration in Agent.
- **Cost:** requires a deliberate multi-tool executor change and deterministic
  test matrix.
- **02-Knowledge recommendation:** choose D1.

### Option D2 — One Composite `research_search` Tool

The composite Tool internally decides between Web and Knowledge.

- **Benefit:** minimal graph change.
- **Cost:** hides orchestration inside a Tool, weakens source-policy visibility,
  and risks making Knowledge control the Research Graph.
- **02-Knowledge recommendation:** reject D2.

### Required Architect Decision

Confirm D1 or D2 and define whether the first integration permits one call to
each Tool, multiple calls per Tool, and partial success. Recommendation: retain
the current deterministic sequential execution and fail the node on any Tool
failure; do not add retries or partial-success semantics without a separate
Contract.

## Proposed Trust and Data Flow

```text
Authenticated/trusted upstream
  → immutable KnowledgeScope(user_id, project_id) outside Agent State
  → Agent researcher chooses web_search and/or knowledge_search
  → knowledge_search typed client
  → Product Backend /projects/{project_id}/knowledge/search
  → Backend verifies owner_user_id + project_id
  → exact Knowledge retrieval
  → KnowledgeHit[]
  → approved KnowledgeHit-to-Evidence mapping
  → one Agent Evidence collection
  → Writer / later Citation mapper
```

The Evidence item may retain source identifiers for provenance, but it does not
become authorization authority. Every later Knowledge request is independently
authorized by Backend.

  Citation/Evidence Contract change.

## P7-000 Acceptance Criteria

- Scope carrier and scope authority are named separately.
- No browser value, model Tool argument, Agent State field, or thread metadata
  is accidentally described as authorization authority.
- Agent invokes a stable Knowledge boundary and remains unaware of pgvector,
  chunking, embeddings, and retrieval SQL.
- The approved Evidence Contract preserves Document/Chunk provenance and does
  not create parallel source-specific evidence collections.
- Temporary Web, permanent upload, and future Saved Web lifecycles remain
  distinct.
- Multi-tool ownership stays in Agent rather than Knowledge.
- No P7-001 code begins until 00-Architect records the decisions.
