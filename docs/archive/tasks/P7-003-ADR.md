# P7-003 — Citation Mapping and Retrieval Evaluation Hooks

**Status:** DONE — 00-Architect accepted A1 + B1 on 2026-09-13; P7-003B /
P7-003C are implemented and Phase 7 exit was accepted on 2026-09-14.

## Architect Decision

### Citation: A1, Agent State + output

- 01-Agent owns a pure Evidence-to-Citation projection and wires `citations`
  into `AgentState` and `AgentOutputState`. It is not a Knowledge or Frontend
  model.
- `report` and `citations` are returned by the same Writer node update. This
  keeps the latest successful Report and its Citation list coherent if a later
  run is still active or fails before Writer completes.
- Citation IDs are the run-local ordinals `c1`, `c2`, ... in validated Evidence
  order. They are not UUIDs, Product identities, durable cross-run references,
  or substitutes for `run_id`.
- Mapping preserves Evidence order and duplicates. It never parses
  `ToolMessage.content`, report prose, filenames, or retrieval scores.
- `excerpt` is deterministic: strip leading/trailing whitespace; if the result
  exceeds 500 Unicode code points, retain the first 499 and append `…`.
  `source_label` and approved source-specific provenance are copied from the
  validated Evidence item. Retrieval score and relevance note do not become
  Citation fields.
- A successful no-Tool path returns `citations: []`. Inline `[c1]` markers,
  claim-to-source attribution, citation correctness, Citation UI, PostgreSQL
  persistence, and historical replay are not claimed by this projection.
- Compatibility policy is a clean development-checkpoint break. No migration
  or fallback parser is added; acceptance uses a fresh thread. Existing local
  checkpoint data is not deleted by the implementation task.

### Retrieval evaluation: B1, logical fixture + Recall@5 baseline

- 05-Quality owns the versioned fixture, metric implementation, and result
  report. 02-Knowledge reviews chunk/retrieval semantics; 03-Backend reviews
  use of the existing scoped API. Neither module changes production behavior
  merely to make the evaluation pass.
- The source-controlled JSON fixture uses `project_key`, `document_key`, and
  zero-based `chunk_index`, never generated UUIDs. Documents are declared once
  per logical Project; cases reference them by logical key.
- The harness creates isolated test users/Projects, ingests the fixture through
  the existing Product Backend Document API, and resolves generated
  `document_id` / `chunk_id` only inside evaluation setup. It does not add a
  Chunk API or expose test identities as a Product Contract.
- The system under evaluation is the existing scoped Knowledge search API with
  the configured `BAAI/bge-m3` embedding path and pgvector. Deterministic unit
  tests may use controlled ranks only to verify fixture validation, resolution,
  and metric arithmetic.
- The first metric is per-case and macro **Recall@5**:
  `|relevant passages ∩ top-5 passages| / |relevant passages|`. The first run
  records a baseline and has no pass/fail quality threshold. MRR, NDCG,
  Precision@K, answer faithfulness, and citation correctness remain later
  decisions.

The split is intentional: Citation projection changes the 01-Agent output
Contract, while retrieval ground truth and metrics belong to 05-Quality. They
share this ADR but are independently reviewable and neither depends on the
other's implementation.

## Why this is the next segment

P7-001 and P7-002 establish a single, validated Agent Evidence union. P7-FE-001
now transports Project scope and the stream regression is closed. The remaining
high-value boundary is to make this durable provenance consumable as Citations
and to provide fixed retrieval ground truth for Quality, without prematurely
building a citation UI or changing retrieval algorithms.

This changes the Agent output Contract and introduces shared evaluation-data
meaning, so 02-Knowledge and 05-Quality cannot decide it independently.

## Current facts

- `temporary_research` Evidence already has URL provenance.
- `user_upload` Evidence already has `document_id`, `chunk_id`, and `filename`.
- Evidence order is deterministic: model Tool-call order, then each Tool's
  result order.
- `report` is currently the sole stable Agent output; it does not contain
  inline citation markers.
- `KnowledgeHit.score` is a diagnostic retrieval value, not a calibrated
  relevance or citation-correctness score.
- No versioned retrieval ground-truth set, Recall@K result, MRR, NDCG, or
  citation-correctness result is currently claimed.

## Non-negotiable boundaries

- Keep one Evidence collection. Do not create parallel Web and Knowledge
  citation systems.
- Citation provenance is presentation/reference data, never authorization
  authority. Project/user scope remains enforced at every Backend retrieval.
- Do not infer a citation from report text, a filename alone, or a retrieval
  score threshold.
- Saved Web Source remains unimplemented. Do not add a speculative source type
  or persistence lifecycle in this segment.
- Do not add BM25, hybrid retrieval, RRF, reranking, ANN tuning, query rewrite,
  benchmarks, or a citation UI before a measured need and separate task exist.
- The Quality fixture must use logical fixture identities, not random runtime
  UUIDs as checked-in ground truth.

## ADR-P7-003-A — Citation output shape and owner

### Option A1 — Run-local deterministic Citation output (recommended)

Agent maps the validated Evidence list into a separate, ordered `citations`
output. Citation IDs are run-local ordinals (`c1`, `c2`, …), assigned after
Evidence aggregation. Each Citation contains:

```text
Citation
  citation_id: string                 # run-local ordinal
  source_type: temporary_research | user_upload
  source_label: string
  excerpt: string                     # deterministic bounded excerpt
  provenance:
    TemporaryWebCitation { url, captured_at? }
    ProjectDocumentCitation { document_id, chunk_id, filename,
                              page_number?, section_path? }
```

The mapping is pure and deterministic; it preserves Evidence order and does
not deduplicate. `citations` becomes an explicit Agent output/state field beside
`report`. This task does **not** require inline `[c1]` text in the Report or a
Frontend renderer.

**Benefits:** preserves current provenance, produces a direct future UI/API
contract, avoids new IDs on every Evidence variant, and remains source-neutral.

**Costs:** adds a versioned Agent output field and requires a clean checkpoint
schema break like P7 Evidence did.

### Option A2 — Add a permanent `evidence_id` to every Evidence item

Each Tool manufactures a stable Evidence ID; Citation references it.

**Benefit:** direct one-to-one references.

**Cost:** changes all Tool outputs, validation, State serialization, and
checkpoint compatibility; “stable” identity semantics are unclear for repeated
or changed Web results. This is more machinery than the current product needs.

### Option A3 — Let Frontend parse report text into citations

**Reject:** reports are model text, not an authoritative provenance mapping;
parsing creates an implicit and brittle Citation Contract.

## ADR-P7-003-B — Retrieval ground-truth fixture boundary

### Option B1 — Versioned logical fixture manifest (recommended)

Commit a small, source-controlled fixture manifest containing:

```text
RetrievalFixtureV1
  projects: [{
    project_key
    documents: [{ document_key, filename, Markdown content }]
  }]
  cases: [{
    case_id
    project_key
    query
    relevant_passages: [{ document_key, chunk_index }]
  }]
```

The test harness ingests those documents into an isolated test Project and
resolves runtime UUIDs only while evaluating a run. Quality can then compute
Recall@K from the resolved relevant chunk IDs without committing generated IDs.
P7-003C implements manifest validation, the resolver, and the first Recall@5
baseline. 05-Quality owns result reporting and future dataset changes; later
metrics and thresholds require review rather than arriving implicitly.

**Benefits:** reproducible inputs, durable relevance intent, no production data,
and no API change merely to expose a chunk index.

**Costs:** fixture maintenance must accompany any intentional chunking-rule
change.

### Option B2 — Check in random runtime `document_id` / `chunk_id` values

**Reject:** ingestion generates UUIDs, so fixtures would be invalid or would
require test-only persistence behavior.

### Option B3 — Treat top-1 returned filename as ground truth

**Reject:** filename cannot distinguish passages, does not support Recall@K,
and hides chunking regressions.

## 02-Knowledge recommendation

The accepted **A1 + B1** path is the smallest domain-neutral path from already
validated provenance to citation-grade references and metric-ready retrieval
fixtures. It leaves presentation, retrieval optimization, Saved Web, and
production security for separately scoped work.
