## Key Decisions

- The Knowledge Tool is constructed per node execution from frozen Run context;
  no scoped Tool or identity is checkpointed.
- Registry order is stable and model-visible, but model call order controls
  sequential execution and Evidence order.
- A later Tool failure may follow an already-completed external search, but the
  failing node returns no ToolMessage or partial Evidence State update.
- Frontend scope injection is intentionally not implemented across the
  04-Frontend boundary.

## What the user should understand

1. `AgentContext` is a per-run dependency carrier, not Agent State and not an
   authorization authority.
2. Both nodes rebuild the registry from the same Run context, so
   `knowledge_search` closes over the current run's immutable Project scope.
3. Name pre-validation prevents a valid earlier call from running when any
   requested Tool name is unknown.
4. Sequential execution preserves model-call and Evidence order; a thrown
   error aborts the node before State or Writer receives partial results.

## Acceptance Criteria

- Run context accepts exactly one immutable `knowledge_scope` with UUID
  `user_id` and `project_id`; neither value enters State or Tool arguments.
- The Researcher sees exactly `web_search` and `knowledge_search`, with
  parallel Tool calls disabled.
- Every requested Tool name is validated before any Tool executes.
- Valid calls execute sequentially in model order; repeated calls are allowed.
- Evidence from both Tools is validated through the same Evidence union and
  flattened in call/result order.
- Any Tool or Evidence-validation failure fails the node, produces no State
  update, and prevents Writer execution; no retry or partial success is added.
- Web Evidence is never passed to Knowledge ingestion or indexing.
- A local Agent-boundary smoke proves Project A cannot retrieve Project B
  Knowledge and vice versa for the same owner.
- Existing Agent, Backend, and Knowledge tests remain green.
