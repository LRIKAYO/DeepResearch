## Transaction and Authority Boundary

The create path validates the Project first and ends that read transaction
before calling Agent Server. Thread creation is external to the PostgreSQL write
transaction. A successful SDK response supplies the opaque `thread_id`, after
which the Backend inserts and commits the association. If that write fails, the
Backend rolls back and makes one best-effort delete without replacing the
original database failure.

PostgreSQL remains authoritative for Project/session membership. Agent thread
metadata is a diagnostic projection, and Agent Server remains authoritative for
thread and run execution resources.

## Gate B — PAIR Learning Review

**Status:** PASSED — user explanation recorded on 2026-08-31

The user personally authored the initial Agent Server and Research Session
create-path files, participated in their review, and then explained the five
required boundaries:

1. validate the Project before creating the thread, then persist the
   session/thread mapping;
2. `research_session_id` is the product identity, `thread_id` is the
   conversation execution container, and `run_id` identifies one execution;
3. one session/thread may carry several runs, with no current product need to
   persist those runs;
4. PostgreSQL decides Project/session membership, while Agent metadata is only
   a diagnostic projection;
5. Agent creation failure needs no compensation, whereas database failure after
   thread creation triggers one best-effort delete while preserving the
   original database exception.

This explanation satisfies the P4-001 PAIR learning acceptance criterion.
