## Findings

### QF-006 — Local Agent-server restart does not provide durable conversation retention

- Severity: **Low for the declared local/test release; release blocker for any
  durability claim**.
- Evidence: after the credentialed in-memory Agent Server exited, PostgreSQL
  still contained Research Session/thread associations while a fresh local
  Agent Server did not contain their completed checkpoint State.
- Impact: browser refresh works while the local Agent runtime retains the
  thread, but Agent-server process restart is not a durable replay guarantee.
- Required action: before claiming durable daily-use history or production
  recovery, decide checkpoint persistence (for example PostgresSaver or a
  deployed LangGraph persistence boundary) and stale-session reconciliation.
  Do not patch this inside Frontend.

### Local PostgreSQL collation warning

The reused development volume reports a host collation-version mismatch
(`2.41` when created versus current `2.36`). Queries, migrations, and tests
passed. This is local environment maintenance, not a Phase 8 code defect; a
future Backend maintenance task should rebuild affected collation-dependent
objects and refresh the database version if the warning persists.

## What the user should understand

1. Upload/list traffic goes from Frontend to Product Backend and is scoped by
   the selected Project; no Research Session is needed.
2. Research traffic goes from Frontend to LangGraph Server; Run context carries
   Project scope, and the Agent calls Product Backend for Knowledge.
3. Sources comes from the matching latest successful checkpoint `citations`,
   not ToolMessage text. A failed later run does not turn failure into an empty
   success or overwrite the previous Report/Sources pair.
4. Browser reload and Agent-server process restart are different guarantees.
