Key Decisions:

- Recommend versioned `pgvector/pgvector:0.8.6-pg18`, measured locally as
  PostgreSQL 18.6 with pgvector 0.8.6.
- Recommend the user-approved `BAAI/bge-m3` model, measured at 1024 dimensions.
- Recommend fixed `vector(1024)` and cosine distance using ascending `<=>`.
- Treat the HNSW smoke only as operator/index compatibility evidence, not as a
  production index decision or retrieval-quality claim.
- Enforce Project isolation in the authoritative Chunk-to-Document query; a
  globally closer row from another Project must never leave that boundary.

Validation:

- Used an isolated `--rm` container with tmpfs storage and no named/host volume;
  the existing `researchflow_postgres_data` volume was never mounted.
- Created the `vector` extension, inserted representative synthetic vectors,
  and verified cosine ordering, limit behavior, empty results, and two-Project
  isolation.
- Generated three real finite `BAAI/bge-m3` vectors with stable dimension 1024.
- Inserted and queried the real vectors through `vector(1024)`; a wrong-dimension
  vector was rejected with SQLSTATE `22000`.
- Created an HNSW `vector_cosine_ops` index and observed a compatible `<=>`
  index plan.
- Recorded only model/dimension/timing/result metadata; no credential or full
  vector is persisted in repository artifacts.
- Architect replay used a fresh tmpfs container, preserved the existing named
  volume, excluded a globally closer cross-Project row through
  `documents.project_id`, and removed the temporary container.
- Architect did not repeat the external embedding call because no provider
  credential was present in that process; P6-002 retains a real configured
  provider smoke as its own acceptance gate.
- `git diff --check` is the final repository formatting gate.

What the user should understand:

- Embedding dimension is a physical schema fact: this model returns 1024 values,
  so a fixed `vector(1024)` accepts it and rejects a two-dimensional value.
- `<=>` calculates cosine distance and smaller values sort first.
- The unfiltered nearest row belonged to Project B at distance zero; the
  authoritative `WHERE project_id = ...` boundary prevented it from appearing
  in Project A's result.
- The embedding provider produces numbers, pgvector stores/orders them, and
  `KnowledgeHit` will later preserve Document/Chunk provenance; these are
  different responsibilities.
